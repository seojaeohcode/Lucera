# 루체라 설치 예정지 사전점검·운영형 민원 지도 기획서

> 설치하려는 위치를 입력하면 설치를 재검토해야 하는 이유를 근거와 함께 설명하고, 운영 중 발생한 민원을 다시 지도 데이터로 축적하는 **입지 사전점검·민원 지식 플랫폼**으로 확장한다.

## 1. 기획 배경

루체라는 태양광 발전사업 예정지 주변의 과거 주민 반대·민원·협의·환경 쟁점을 지도와 원문 근거로 확인하는 서비스로 시작한다.

서비스가 실제 기관·사업 현장에 도입되면 새로운 민원은 계속 발생한다. 이때 민원을 단순히 접수하고 종결하는 데서 끝내지 않고, 담당자가 민원의 원인과 실제 발생 지점을 조사한 뒤 결과를 지도에 기록한다.

그 결과 루체라의 지도는 다음 두 종류의 기록이 함께 쌓이는 구조가 된다.

1. **도입 전 기록**: 공개 회의록·공식 문서에서 수집한 과거 민원 및 갈등 사례
2. **도입 후 기록**: 서비스 이용 중 접수되어 조사·검증을 거친 실제 민원 사례

시간이 지날수록 지도에는 지역별 민원 이력, 반복되는 원인, 해결 과정이 누적된다. 이 데이터는 다음 사업의 사전 검토뿐 아니라 현재 사업의 주민 대응과 재발 방지에도 활용된다.

## 2. 핵심 사용 장면

사용자가 태양광 발전시설을 설치하려는 주소나 필지를 입력한다. 루체라는 해당 위치를 중심으로 과거 공개 기록과 도입 후 누적된 민원 사건을 검색하고, 입지·주민·환경·안전·인허가 관점에서 설치를 재검토해야 하는 이유를 설명한다.

```text
설치 예정지 입력
      ↓
주변 과거 기록 + 누적 민원 핀 + 위치·입지 정보 조회
      ↓
반복 쟁점·위험 요인·이해관계자·과거 조치 분석
      ↓
"왜 주의해야 하는가"를 근거 문장·지도·사례와 함께 설명
      ↓
검토 항목과 다음 조치 제안
```

결과는 단순한 점수나 `설치 가능/불가` 두 글자가 아니다. 사용자가 실제 검토를 이어갈 수 있도록 **문제가 될 수 있는 이유, 그 이유를 뒷받침하는 근거, 확인이 필요한 사항**을 함께 제시한다.

## AI 활용 전략

루체라에서 AI는 질문에 답하는 챗봇이 아니라, 흩어진 민원 기록을 구조화하고 설치 예정지와 연결해 **근거 있는 사전점검 결과를 만드는 분석 엔진**으로 활용한다.

### 1. AI가 해결할 핵심 문제

민원 데이터에는 같은 의미를 가진 다양한 표현, 불완전한 주소, 제보자의 주장과 확인된 사실이 섞여 있다. 사람이 모든 문서를 읽어 비교하면 시간이 오래 걸리고, 새로운 민원이 들어올 때마다 기존 사례와의 관계를 다시 찾아야 한다.

AI는 이 과정을 다음처럼 보조한다.

| 단계 | AI 활용 | 결과 |
|---|---|---|
| 민원 이해 | 민원 원문에서 현상·피해·요구·긴급도를 추출 | 구조화된 민원 요약 |
| 쟁점 분류 | 빛반사·소음·경관·배수·안전·협의 등 복수 유형 분류 | 쟁점 태그와 분류 근거 |
| 위치·대상 추출 | 주소·마을·시설명·사업명·도로·하천 등 개체 추출 | 위치 후보와 관련 대상 |
| 사건 묶기 | 기존 사건과 의미·위치·시점·대상을 비교 | 신규·중복·후속 사건 후보 |
| 유사 사례 검색 | 키워드와 임베딩을 함께 사용해 과거 사례 검색 | 비교 가능한 근거 사례 |
| 위험 요약 | 검색된 근거만 읽고 설치 재검토 사유를 생성 | 사유·근거·추가 확인 항목 |
| 핀 등록 보조 | 핀 제목·요약·쟁점·위치 정밀도 초안 생성 | 담당자 검토용 핀 초안 |
| 운영 학습 | 담당자의 수정·승인·반려 결과를 다음 분류에 반영 | 점점 정확해지는 분류·검색 |

### 2. 설치 예정지 점검에서의 AI 동작

AI가 처음부터 결론을 상상해서 만드는 방식이 아니라, **검색 가능한 사실을 먼저 모으고 그 범위 안에서 설명을 생성하는 검색증강형 구조(RAG)**를 사용한다.

```text
설치 예정지 주소
  → 주소·좌표·행정구역 정규화
  → 지도·DB에서 주변 사실 검색
  → 키워드 + 임베딩으로 유사 민원 검색
  → AI가 쟁점·원인·영향 위치·반복성 분석
  → 근거 검증기에서 인용 가능 문장 확인
  → 사전점검 결과·설명·체크리스트 생성
  → 담당자 승인 후 사용자에게 제공
```

사전점검 결과의 각 사유는 다음 형식으로 생성한다.

```json
{
  "reason": "인근 주거지에서 빛반사 민원이 반복됨",
  "category": "운영·피해 가능성",
  "evidence": [
    {
      "case_id": "case-001",
      "source": "공식 회의록",
      "excerpt": "인근 주택에서 반사광으로 인한 불편이 제기됨",
      "location_relation": "same_village",
      "date": "2025-04-12"
    }
  ],
  "confidence": "medium",
  "next_check": "모듈 방향과 시간대별 반사 시야를 현장 검토"
}
```

즉 AI의 답변은 “설치하면 안 됩니다”로 끝나지 않고 다음 네 가지를 포함해야 한다.

1. 어떤 문제가 우려되는가
2. 어떤 과거·현재 기록이 그 판단을 뒷받침하는가
3. 해당 기록과 예정지의 위치·사업·쟁점 연결은 얼마나 정확한가
4. 확정하기 위해 무엇을 추가로 조사해야 하는가

### 3. AI 기능의 상세 설계

#### A. 민원 원문 구조화

민원 제보, 회의록, 현장 메모, 조사 보고서에서 다음 정보를 추출한다.

- 민원 현상: 무엇이 불편하거나 피해를 주었는가
- 대상 시설: 어떤 설비·공사·사업과 관련되는가
- 영향 위치: 주민·도로·건물·농지 등 어디에서 문제가 나타났는가
- 원인 후보: 빛반사, 소음, 배수, 공사 차량, 협의 부족 등
- 시점·반복성: 언제 시작했고 반복되는가
- 주장과 사실: 제보자의 주장인지, 조사로 확인된 사실인지
- 요구사항: 보완, 중단, 보상, 설명회, 재조사 등

추출 결과에는 원문 문장 위치와 모델 신뢰도를 함께 저장한다. 원문에서 근거를 찾지 못한 값은 생성하지 않고 `unknown`으로 둔다.

#### B. 위치·원인 관계 추론

AI는 문장 안에서 “어디서 불편을 느꼈는지”와 “무엇이 원인으로 지목되었는지”를 분리한다.

```text
주민이 경험한 장소 → 영향 위치
문제가 발생한 설비·공사 → 원인 위치
사업의 필지·시설 → 관련 사업 위치
```

AI가 추출한 위치는 주소 DB·지명사전·지도 좌표와 대조한다. 대조되지 않은 위치는 후보로만 보존하며, AI 추론만으로 지도에 정확한 좌표를 확정하지 않는다.

#### C. 유사 사례·중복 민원 검색

검색은 키워드 검색과 의미 검색을 결합한다.

- 키워드 검색: `빛반사`, `주민반대`, `배수`, `이격거리` 등 명시적 단어 확인
- 의미 검색: 표현은 다르지만 같은 문제를 말하는 사례 검색
- 공간 검색: 정확 좌표·주소·리·읍면·시군 단위 연결
- 시간 검색: 동일 사업의 후속 민원, 조치 전후 변화 확인
- 구조화 필터: 쟁점, 시설 유형, 사업, 상태, 공개 수준 필터링

AI는 검색 결과를 근거로 신규 민원·기존 사건의 추가 제보·유사 사례를 구분한다. 같은 지역이라는 정보만으로 중복 사건을 확정하지 않는다.

#### D. 근거 기반 위험 설명

AI는 상위 검색 결과에 포함된 문서·문단·조사 증빙만 사용해 사전점검 설명을 작성한다. 생성된 모든 문장은 다음 중 하나로 표시한다.

| 표시 | 의미 |
|---|---|
| `fact` | 원문·공식 자료·조사 결과에서 직접 확인된 사실 |
| `inference` | 여러 사실을 바탕으로 도출한 가능성 또는 비교 판단 |
| `recommendation` | 추가 조사·설계·협의가 필요하다는 권고 |
| `unknown` | 자료가 부족해 판단할 수 없는 내용 |

`fact`와 `inference`를 화면에서 시각적으로 구분하고, `inference`에는 반드시 연결된 근거를 표시한다. 검색 결과에 없는 법령 기준·위치·피해 사실을 AI가 만들어내지 못하도록 인용 검증 단계를 둔다.

#### E. 담당자 검수 보조

AI는 다음 작업을 자동 확정하지 않고 담당자에게 초안을 제안한다.

- 민원 유형과 긴급도
- 기존 사건과의 중복·후속 관계
- 원인 위치와 영향 위치
- 지도 핀 제목·요약·공개 범위
- 설치 재검토 사유와 추가 확인 체크리스트

담당자가 승인·수정·반려한 결과는 학습 데이터로 저장한다. 이후 모델의 분류와 검색 품질을 평가할 때 이 검수 결과를 정답 데이터로 사용한다.

### 4. AI 대회에서 보여줄 차별점

루체라의 AI 포인트는 “민원 내용을 요약해 주는 챗봇”이 아니라 다음의 폐쇄형 데이터 루프다.

```text
과거 문서 학습·검색
  → 설치 예정지 위험 설명
  → 실제 민원 접수
  → AI의 원문 구조화·유사 사건 연결
  → 담당자 조사·검수
  → 검증된 지도 핀과 해결 이력 축적
  → 다음 설치 예정지 판단의 정확도 향상
```

대회 시연에서는 하나의 주소를 입력한 뒤 다음 화면을 연속으로 보여준다.

1. 예정지 주변의 과거·현재 민원 핀 표시
2. AI가 가장 중요한 설치 재검토 사유 3개 제시
3. 각 사유에 연결된 원문 문장과 지도 관계 표시
4. “확인된 사실 / AI가 추론한 위험 / 추가 조사” 구분
5. 담당자가 핀을 승인하거나 수정
6. 새 민원을 등록하면 기존 사례와 연결되고 지도에 후속 핀이 쌓이는 과정 시연

### 5. AI 성능 평가 지표

AI를 사용했다는 사실보다 실제로 근거 있는 결과를 만드는지가 중요하므로 다음 지표를 관리한다.

| 지표 | 평가 내용 |
|---|---|
| 쟁점 분류 F1 | 빛반사·소음·경관·배수 등 민원 유형 분류 정확도 |
| 위치 추출 F1 | 주소·시설·영향 위치 추출 정확도 |
| 유사 사례 Recall@K | 상위 K개 결과 안에 정답 사례가 포함되는 비율 |
| 중복 사건 정확도 | 신규·후속·중복 사건 연결의 정확도 |
| 근거 인용 정확도 | 생성 설명이 실제 원문과 일치하는 비율 |
| 환각률 | 검색 근거에 없는 사실을 생성한 비율 |
| 핀 승인율 | 담당자가 수정 없이 승인한 AI 핀 초안의 비율 |
| 처리 시간 단축 | 사람이 처음부터 처리할 때 대비 조사 시간 감소 |

### 6. AI 안전장치

1. AI는 법적 허가·불허를 최종 판정하지 않는다.
2. 검색된 근거가 없으면 결론 대신 `판단 보류`를 반환한다.
3. 좌표가 없으면 AI 추론으로 정확한 점을 만들지 않는다.
4. 원문 인용과 AI 요약을 구분해 표시한다.
5. 민원인의 개인정보는 AI 입력 전에 마스킹한다.
6. 확인되지 않은 주장을 공개 핀이나 확정 사실로 표시하지 않는다.
7. 모든 AI 결과에 모델 버전·생성일·근거 ID·검수 상태를 저장한다.

## 3. 제품 정의

루체라는 민원을 자동으로 판정하거나 허가 여부를 결정하는 시스템이 아니다.

민원과 관련된 사람의 제보, 담당자의 조사 결과, 공식 문서와 현장 근거를 하나의 이력으로 연결해 다음 질문에 답하는 **근거 기반 민원 조사·지도화 도구**다.

- 어디에서 민원이 발생했는가?
- 실제 문제를 일으킨 대상 또는 원인은 무엇인가?
- 같은 장소·사업·쟁점에서 과거에도 유사한 민원이 있었는가?
- 민원은 현재 어떤 상태이며, 어떤 조치가 이루어졌는가?
- 다음 사업이나 현장 대응에서 무엇을 미리 확인해야 하는가?
- 이 위치에 설치하려 할 때 어떤 문제가 발생할 가능성이 있는가?
- 설치를 재검토해야 한다면 그 이유와 원문 근거는 무엇인가?

### 3.1 설치 불가 판단의 범위

루체라가 설명하는 “설치하면 안 되는 이유”는 다음 네 가지를 구분한다.

| 구분 | 의미 | 루체라의 표현 |
|---|---|---|
| 법·제도상 제한 | 법령·조례·보호구역·허가 기준 등 공식 기준에 따른 제한 | 공식 기준과 확인 필요 항목을 제시하며, 최종 허가 판단은 담당 기관에 맡긴다. |
| 입지 위험 | 산지·농지·배수·재해·경관·이격거리 등 위치 자체의 위험 | 해당 위치에서 문제가 될 수 있는 요소와 확인 근거를 설명한다. |
| 주민·사회적 갈등 | 동일 지역의 반대·집단민원·협의 실패·보상 갈등 등 | 과거 사례와 반복 쟁점을 보여주고 사전 협의 필요성을 설명한다. |
| 운영·피해 가능성 | 빛반사·소음·교통·안전·토사 유출 등 운영 또는 공사 중 예상되는 문제 | 유사 사례와 원인·영향 위치를 연결해 예상 리스크를 설명한다. |

따라서 화면의 결론은 근거 수준에 따라 다음처럼 표현한다.

- **설치 재검토 필요**: 명확한 제한 또는 중대한 반복 위험이 확인됨
- **조건부 검토**: 특정 조사·협의·설계 보완을 완료해야 함
- **주의해서 검토**: 유사 사례나 위치 위험이 있으나 확정 판단에는 추가 확인이 필요함
- **확인된 위험 없음**: 현재 보유한 데이터에서 주요 위험이 확인되지 않음
- **판단 보류**: 주소·좌표·근거가 부족해 결론을 내릴 수 없음

`확인된 위험 없음`은 문제가 없다는 보증이 아니며, `설치 재검토 필요`도 법적 불허를 자동 확정하는 값이 아니다. 모든 결론에는 판단 근거, 데이터 기준일, 위치 정밀도, 추가 확인 항목을 함께 표시한다.

## 4. 설치 예정지 사전점검 기능

### 4.1 입력 정보

사용자는 최소한 설치 예정지 주소를 입력한다. 정확도를 높이기 위해 다음 정보를 추가로 받을 수 있다.

| 입력 | 활용 |
|---|---|
| 설치 예정지 주소·필지 | 행정구역, 좌표, 주변 사례 검색의 기준 |
| 사업 유형·설비 규모 | 태양광 시설 유형과 설비용량(kW/MW)에 따른 비교 |
| 부지면적·설치면적 | 전체 사업 부지와 실제 설비 설치 면적(㎡)에 따른 밀도·입지 비교 |
| 모듈 방향·높이·배치 | 빛반사·경관·조망 가능성 검토 |
| 주변 주거지·도로·농지·하천 | 영향 위치와 생활권 위험 검토 |
| 예정 공사 기간·차량 동선 | 공사 소음·교통·안전 위험 검토 |
| 현재 확보한 허가·협의 자료 | 공식 문서와 입력값의 근거 연결 |

주소가 읍·면·리 수준이면 그 범위까지만 판단한다. 필지와 좌표가 확인되지 않은 상태에서 특정 건물이나 토지를 임의로 설치 위치로 확정하지 않는다.

사전점검의 핵심 입력은 `설치 예정지 주소`, `부지면적`, `설비용량`이다. `설치면적`은 별도로 알고 있는 경우 추가 입력한다. 부지면적과 설치면적을 구분하지 않고 하나의 면적만 입력하면 어떤 면적인지 명시하고, 자료가 없으면 `unknown`으로 남긴다.

면적은 다음 계산과 비교에 사용한다.

- 설비용량 대비 부지면적: `capacity_kw / site_area_sqm`
- 실제 설치면적 대비 전체 부지면적: `installation_area_sqm / site_area_sqm`
- 동일 지역·유사 규모 사업과의 면적·용량 비교
- 개발행위·농지·산지·배수·경관 검토가 필요한 규모인지 확인

이 계산은 입지 검토를 위한 판단 재료이며, 면적만으로 설치 가능·불가를 확정하지 않는다. AI가 면적을 임의로 만들어내지 않고, 사용자 입력·허가 원장·공식 문서에 있는 값만 사용한다. 값이 추정치인 경우에는 `estimated` 배지와 추정 근거를 표시한다.

### 4.2 분석 영역

설치 예정지 사전점검은 다음 네 개의 분석 카드를 기본으로 제공한다.

#### A. 과거 민원·갈등 이력

- 같은 필지·시설·사업에 대한 기존 민원
- 같은 마을·리·읍면에서 반복된 민원
- 주민 반대, 협의 실패, 집단민원, 보상 갈등
- 과거 민원의 조치 결과와 재발 여부

#### B. 설치 위치·환경 위험

- 빛반사·눈부심이 영향을 줄 수 있는 주거지·도로·공공시설
- 소음·경관·조망·생태·재해 관련 과거 쟁점
- 토사 유출·배수·침수·산사태 등 지형·공사 위험
- 농지·산지·보호구역·이격거리 등 추가 확인이 필요한 입지 조건

#### C. 인허가·절차 위험

- 개발행위·환경 검토·농지·산지 관련 확인 항목
- 주민 설명회·동의·협의가 필요한 사안
- 관련 조례·공식 기준·행정기관 검토가 필요한 부분
- 자료가 부족해 아직 확인하지 못한 절차

#### D. 예상 영향과 대응 항목

- 영향 받을 수 있는 위치와 원인 시설의 관계
- 사전에 준비해야 할 현장 조사·측정·시뮬레이션
- 주민 협의에서 설명해야 할 항목
- 설계 변경·차폐·배수 보완·공사 시간 조정 등 검토 가능한 대응

### 4.3 결과 화면

사용자가 주소를 입력하면 다음 순서로 결과를 보여준다.

1. **종합 판단**: 재검토 필요·조건부 검토·주의·위험 없음·판단 보류
2. **설치하면 안 되거나 주의해야 하는 이유**: 최대 3~5개의 핵심 사유
3. **지도 근거**: 예정지, 과거·현재 민원 핀, 영향 위치, 원인 위치
4. **사례 근거**: 유사 사건의 요약과 원문 문장·출처
5. **확인된 사실과 추정의 구분**: 공식 확인·조사 결과·추정 위험을 분리
6. **추가 확인 체크리스트**: 담당자가 다음에 해야 할 조사·협의
7. **데이터 한계**: 검색 범위, 기준일, 좌표 정밀도, 누락 가능성

예시 문구는 다음과 같다.

> 이 예정지 반경 내에서 빛반사 관련 민원 2건과 경관·주민 협의 관련 사례 1건이 확인되었습니다. 과거 사례에서는 인근 도로와 주거지에서 눈부심이 보고되었으므로, 모듈 방향·반사 시야·발생 시간대를 사전에 검토해야 합니다. 현재 기록만으로 설치 불가를 확정할 수는 없으며, 현장 시뮬레이션과 주민 협의를 권고합니다.

핵심 사유는 반드시 `case_id`, `episode_id`, 원문 문단, 출처 URL 또는 조사 증빙과 연결한다.

### 4.4 의정회의록의 주소 해석 원칙

의정회의록에 나오는 주소나 지명이 항상 문제 발생 지역을 의미하는 것은 아니다. 하나의 회의록 안에도 사업 부지, 피해가 나타난 장소, 민원인의 거주지, 회의 장소, 행정기관 소재지가 함께 등장할 수 있다.

따라서 주소를 발견했다고 바로 지도에 문제지역 핀을 만들지 않는다. 먼저 원문 문맥에서 그 장소의 역할을 분류하고, 역할별로 지도 검색·거리 계산·공개 여부를 다르게 적용한다.

| 장소 역할 | 의미 | 사전점검·지도 활용 |
|---|---|---|
| `source_location` | 민원의 원인으로 지목된 태양광 시설·공사·사업 부지 | 설치 예정지와 비교하는 핵심 위치 |
| `impact_location` | 빛반사·소음·배수·교통 불편이 실제로 나타난 장소 | 영향 범위와 피해 사례를 설명하는 위치 |
| `complainant_location` | 민원인 또는 주민의 거주지·주소지 | 개인정보 보호를 위해 정확한 공개 핀으로 사용하지 않으며, 필요하면 마을·행정구역 단위로 집계 |
| `meeting_location` | 의회·위원회·주민설명회가 열린 장소 | 문제지역으로 보지 않고 회의 개최 맥락으로만 저장 |
| `jurisdiction_location` | 행정기관·의회가 관할하는 지역 | 같은 행정구역 검색의 기준으로만 사용 |
| `mentioned_location` | 역할을 아직 확인하지 못한 장소 표현 | 후보로 보존하고 검수 전 확정 위치로 사용하지 않음 |

예를 들어 다음 문장은 서로 다른 두 장소를 뜻한다.

> “○○면 주민이 인근 태양광 시설의 빛반사로 민원을 제기했다.”

- `○○면`: 민원인의 생활권 또는 영향 위치 후보
- `태양광 시설`: 원인 시설 위치 후보
- 실제 설치 필지: 주소·문서·현장 조사로 확인되기 전까지 미확정

위 문장만으로 ○○면의 중심점을 태양광 설치 위치로 만들거나, 주민의 정확한 주소를 공개 핀으로 표시해서는 안 된다.

장소 해석은 다음 순서로 처리한다.

```text
회의록 원문에서 장소 표현 추출
  → 앞뒤 문장에서 장소 역할 판별
  → 주소·지명사전·사업명·시설명과 대조
  → source / impact / complainant / meeting / jurisdiction 분리 저장
  → 근거 문장·정밀도·신뢰도 기록
  → 담당자 검수 후 지도 핀 또는 영역으로 공개
```

AI는 문맥을 읽어 장소 역할을 분류하고 후보를 제안한다. 주소 정규화, 행정구역 대조, 좌표 확인은 데이터베이스와 규칙으로 검증한다. AI와 규칙이 서로 다른 결과를 내거나 원문 역할이 불명확하면 `needs_review`로 남긴다.

사전점검에서 “이 설치 위치 때문에 문제가 생길 수 있다”는 설명을 만들 때는 `source_location`과 `impact_location`을 우선 사용한다. `complainant_location`은 피해를 경험한 생활권을 이해하는 보조 정보이며, 그 자체가 원인 시설 위치라는 뜻은 아니다. 회의 장소와 관할 지역은 거리 위험을 계산하는 대상에서 제외한다.

## 5. 핵심 가치

| 가치 | 설명 |
|---|---|
| 기록의 연속성 | 접수부터 조사, 조치, 종결까지 한 민원의 전체 흐름을 보존한다. |
| 위치의 정확성 | 민원 제보 위치와 실제 원인·발생 위치를 구분해 기록한다. |
| 근거 중심 | 담당자의 판단을 공식 문서·사진·측정값·현장 메모와 연결한다. |
| 재활용성 | 한 번 조사한 결과를 이후 사업의 사전 점검과 유사 사례 검색에 활용한다. |
| 누적성 | 새로운 민원이 처리될 때마다 지역·쟁점·원인·조치 데이터가 지도에 추가된다. |
| 신중한 공개 | 개인정보와 미확정 내용을 보호하고, 검증 상태에 따라 공개 범위를 조절한다. |

## 6. 전체 운영 개념

```text
과거 공개 기록 수집
        ↓
도입 시점의 초기 민원 지도
        ↓
새 민원 접수
        ↓
민원 내용·위치·대상 확인
        ↓
담당자 조사 및 현장 검증
        ↓
원인·발생 지점·관련 사업 확정/보류
        ↓
지도 핀 등록 또는 기존 핀과 연결
        ↓
조치·회신·재발 여부 기록
        ↓
다음 검색·사전 점검·지역 분석에 재사용
```

핵심은 **민원 접수 건수만 지도에 표시하는 것이 아니라, 조사된 사실과 위치를 확인한 뒤 지도 기록으로 승격하는 것**이다.

## 7. 사용자와 역할

### 7.1 민원 제보자

- 민원 내용과 발생 장소를 제보한다.
- 사진·영상·문서 등 증빙을 첨부할 수 있다.
- 개인정보 공개 여부와 연락 가능 여부를 선택한다.
- 본인이 접수한 민원의 처리 상태와 회신을 확인한다.

### 7.2 민원 담당자

- 접수 내용을 확인하고 중복·오접수 여부를 분류한다.
- 민원 발생 위치, 관련 사업·시설, 문제 유형을 조사한다.
- 현장 방문, 관계자 확인, 문서 조회, 측정 등 검증을 수행한다.
- 조사 결과와 근거를 입력한다.
- 지도 핀 등록·수정·보류·비공개 여부를 결정한다.

### 7.3 관리자·분석 담당자

- 지역별 민원 분포와 반복 쟁점을 확인한다.
- 담당자별 처리 현황과 미처리 민원을 관리한다.
- 공개 범위, 개인정보, 보존 기간, 데이터 품질을 관리한다.
- 잘못 등록된 핀이나 중복 사건을 병합·분리한다.

## 8. 운영 후 핵심 사용자 흐름

### 8.1 1단계: 민원 접수

민원은 웹 화면 또는 기관 내부 업무 시스템에서 접수한다.

최소 접수 정보는 다음과 같다.

| 구분 | 입력 내용 |
|---|---|
| 민원 내용 | 주민이 경험한 현상, 불편, 피해, 요구사항 |
| 발생 시점 | 최초 발생일, 반복 여부, 최근 발생일 |
| 제보 위치 | 주소·마을·시설명·지도에서 선택한 위치 |
| 관련 대상 | 태양광 시설, 공사 구간, 도로, 배수로 등 알고 있는 대상 |
| 쟁점 유형 | 빛반사, 소음, 경관, 안전, 토사·배수, 교통, 보상·협의 등 |
| 증빙 | 사진, 영상, 문서, 측정자료, 제보자 설명 |
| 연락 정보 | 회신을 위한 연락처 및 공개 동의 여부 |

접수 직후에는 지도에 확정 핀을 만들지 않는다. 접수 위치에 임시 표시를 할 수는 있지만, 외부 공개 지도에는 `접수됨` 또는 비공개 상태로 둔다.

### 8.2 2단계: 접수 분류·중복 확인

담당자는 접수된 민원을 다음 기준으로 1차 분류한다.

- 신규 민원인지, 기존 민원의 추가 제보인지
- 실제 현장 문제인지, 단순 문의·제안·허위 신고인지
- 위치와 관련 대상이 식별 가능한지
- 긴급한 안전 문제인지
- 개인정보 또는 민감정보가 포함되어 있는지

기존 민원과 동일한 사건이면 새 핀을 만들지 않고 기존 `case`에 추가 이력으로 연결한다. 같은 위치라도 원인·대상·발생 시점이 다르면 별도 민원으로 관리한다.

### 8.3 3단계: 조사 계획 수립

민원 유형과 위험도에 따라 조사 방법을 정한다.

| 유형 | 우선 조사 내용 |
|---|---|
| 빛반사·눈부심 | 발생 방향·시간대, 모듈 방향, 주변 건물·도로, 사진·영상 |
| 소음 | 소음 발생 설비, 시간대, 공사·운영 여부, 측정 필요성 |
| 경관·조망 | 조망 지점, 시설 시야, 가림·반사·색채, 현장 사진 |
| 토사·배수·재해 | 유출 경로, 배수시설, 강우 시점, 공사 구간, 안전 위험 |
| 교통·생활 불편 | 차량 동선, 공사 시간, 통행 방해 지점, 반복성 |
| 주민 협의·보상 | 협의 주체, 약속 내용, 회의·문서, 이행 여부 |
| 인허가·거리 | 사업·시설 위치, 관련 기준, 공식 허가·검토 문서 |

조사 계획에는 담당자, 예정일, 확인할 장소, 필요한 자료, 현장 방문 여부를 남긴다.

### 8.4 4단계: 원인·위치 조사

조사 결과는 민원 내용과 분리해 기록한다. 제보자의 주장과 담당자가 확인한 사실을 섞지 않는 것이 중요하다.

위치는 다음 세 가지를 별도로 관리한다.

| 위치 종류 | 의미 | 지도 처리 |
|---|---|---|
| `reported_location` | 제보자가 민원을 경험했다고 말한 위치 | 접수 위치로 저장, 검증 전 비공개 또는 임시 표시 |
| `impact_location` | 피해·불편이 실제로 나타난 지점 | 조사 결과와 함께 저장 |
| `source_location` | 문제의 원인으로 확인된 설비·공사·시설 위치 | 확정 근거가 있을 때 대표 핀의 기준점으로 사용 |

예를 들어 주민이 마을회관에서 빛반사를 느꼈다고 제보했지만, 원인은 500m 떨어진 특정 태양광 시설로 조사될 수 있다. 이 경우 마을회관은 `impact_location`, 태양광 시설은 `source_location`으로 저장하며 두 위치를 선으로 연결한다.

좌표가 정확하지 않은 경우에는 억지로 중심점을 만들지 않는다. 주소·필지·도로명·리·읍면·시군 단위의 정밀도와 근거를 함께 기록하고, 지도에는 정밀도에 맞는 범위 또는 비공개 상태로 표시한다.

### 8.5 5단계: 조사 결과 검토

조사자는 다음 중 하나로 결론을 기록한다.

| 결과 상태 | 의미 |
|---|---|
| `confirmed` | 원인·대상·위치가 근거로 확인됨 |
| `partially_confirmed` | 민원 현상은 확인되나 원인 또는 위치가 일부 불명확함 |
| `unconfirmed` | 현재 자료만으로 사실 여부를 확인하지 못함 |
| `not_related` | 접수 내용과 해당 사업·시설의 관련성이 확인되지 않음 |
| `duplicate` | 기존 민원 사건과 동일함 |
| `invalid` | 민원으로 처리할 수 없는 문의·오접수·허위 정보 등 |

`confirmed`와 `partially_confirmed`만 자동으로 공개 지도 핀 후보가 된다. `unconfirmed`는 내부 검토용으로 남기고, `not_related`·`invalid`는 공개 지도에 표시하지 않는다.

### 8.6 6단계: 지도 핀 등록

조사 결과가 검토되면 담당자는 다음 방식으로 지도에 반영한다.

1. 기존 핀과 동일 사건인지 확인한다.
2. 동일 사건이면 기존 핀에 새 조사 이력·증빙·조치 결과를 추가한다.
3. 신규 사건이면 새 핀을 생성한다.
4. 핀의 기준 위치와 위치 정밀도를 선택한다.
5. 공개 가능한 정보만 요약해 저장한다.
6. 원문·증빙·조사 기록으로 연결되는 근거를 등록한다.

핀은 단순한 점이 아니라 하나의 `민원 사건 카드`다. 지도에서 핀을 선택하면 요약 정보와 함께 사건의 시간순 이력을 확인할 수 있어야 한다.

### 8.7 7단계: 조치·회신·종결

민원 핀 등록은 처리의 끝이 아니다. 조치와 결과를 계속 기록한다.

- 담당 부서 또는 사업자에 전달
- 현장 조치·설비 보완·공사 시간 조정·안내·보상·협의
- 제보자 회신일과 회신 내용
- 조치 완료 여부
- 후속 확인일과 재발 여부
- 종결 사유 및 담당자

조치 이후 같은 현상이 다시 발생하면 기존 핀에 후속 이력을 추가한다. 원인이 달라졌다면 새 사건으로 분리하고 관련 핀을 연결한다.

## 9. 지도 핀의 상태와 공개 정책

### 9.1 핀 상태

```text
접수됨
  → 조사 중
  → 검토 대기
  → 확인됨 / 일부 확인됨 / 미확인
  → 조치 중
  → 종결
  → 재발·후속 조사
```

상태 변경은 현재 상태만 덮어쓰지 않고 `status_history`로 모두 보존한다.

### 9.2 공개 수준

| 공개 수준 | 노출 내용 |
|---|---|
| `internal` | 원문·개인정보·상세 조사자료를 포함한 내부 전용 기록 |
| `team` | 담당 조직이 공유하는 민원 요약과 조사 상태 |
| `public_summary` | 비식별화된 위치 범위, 쟁점, 상태, 조치 요약 |
| `public_detail` | 공개 가능한 공식 근거까지 포함한 상세 사례 |

기본값은 내부 저장이다. 공개 지도에 표시하기 전 담당자 검토와 비식별화가 필요하다.

## 10. 민원 사건과 지도 데이터 모델

### 10.1 핵심 객체

```text
complaint_report       제보자가 접수한 원본 민원
        ↓
complaint_case         동일 사건으로 묶인 민원 단위
        ├─ investigation 조사 작업·담당자·결과
        ├─ evidence      문서·사진·영상·측정값·현장 메모
        ├─ location      제보 위치·피해 위치·원인 위치
        ├─ action        조치·회신·협의·보상·재발 확인
        ├─ map_pin       지도에 표시되는 비식별 요약
        └─ link          사업·시설·과거 사례와의 연결
```

### 10.2 핵심 필드

| 객체 | 주요 필드 |
|---|---|
| 민원 접수 | 접수번호, 접수일, 원문 내용, 제보자, 채널, 긴급도 |
| 민원 사건 | 사건명, 쟁점 유형, 관련 사업, 상태, 공개 수준, 생성·갱신일 |
| 조사 | 조사자, 조사 방법, 조사일, 사실 요약, 결론, 신뢰도 |
| 위치 | 위도·경도 또는 주소, 위치 종류, 정밀도, 좌표 출처 |
| 근거 | 근거 유형, 파일·URL, 촬영·작성일, 설명, 해시, 공개 가능 여부 |
| 조치 | 조치 유형, 조치 주체, 예정일, 완료일, 결과, 재발 여부 |
| 지도 핀 | 대표 위치, 핀 상태, 공개 요약, 색상·아이콘, 연결 사건 ID |

### 10.3 기존 데이터와의 연결

기존 공개 기록은 `conflict_case`로, 도입 후 접수·조사 기록은 `complaint_case`로 관리한다. 두 객체를 하나로 덮어쓰지 않고 `case_relation`으로 연결한다.

```text
공개 회의록의 과거 사례
  → conflict_case
  → case_relation(similar_to / same_project / follow_up)
  ← complaint_case
  ← 도입 후 실제 민원·조사·조치 이력
```

도입 후 접수된 민원이 과거 공개 기록과 같은 사건으로 확인되면 연결할 수 있다. 단순히 같은 시군·같은 쟁점이라는 이유만으로 동일 사건으로 확정하지 않으며, 연결 근거와 검토자를 남긴다.

## 11. 핀 생성 원칙

모든 접수 건이 핀이 되는 것은 아니다.

### 새 핀을 만드는 경우

- 원인 또는 관련 대상이 신규 사건으로 확인된 경우
- 기존 핀과 위치·사업·발생 시점이 달라 별도 사건인 경우
- 위치 정밀도와 공개 범위를 설정할 수 있는 경우

### 기존 핀에 이력을 추가하는 경우

- 같은 사업·시설·원인에 대한 추가 제보인 경우
- 기존 사건의 후속 민원 또는 재발인 경우
- 같은 조사 건에 대한 새로운 증빙·조치 결과인 경우

### 핀을 만들지 않는 경우

- 단순 문의·제안인 경우
- 사실 여부와 대상 위치를 확인하지 못한 경우
- 개인정보나 명예훼손 우려로 공개할 수 없는 경우
- 기존 사건과 중복되지만 새로운 정보가 없는 경우

이 원칙을 적용해야 지도의 핀 개수가 민원 접수량을 부풀려 보여주는 문제를 막을 수 있다.

## 12. 지도 화면 기획

### 12.1 기본 지도

- 지역·주소·사업명을 검색한다.
- 핀 색상으로 쟁점 또는 상태를 구분한다.
- 기간, 쟁점, 상태, 사업, 조사 결과로 필터링한다.
- 동일 위치의 여러 사건은 클러스터 또는 숫자 핀으로 묶는다.
- 위치 정밀도가 낮은 사건은 정확한 점 대신 영역·리 단위로 표현한다.

### 12.2 핀 상세 카드

핀을 선택하면 다음을 보여준다.

- 민원 요약
- 접수일·발생 시점·최근 갱신일
- 쟁점 유형과 관련 사업·시설
- 제보 위치와 원인 위치의 관계
- 조사 결과와 신뢰도
- 처리 상태와 조치 이력
- 공개 가능한 근거 및 출처
- 유사 과거 사례

### 12.3 시간축 보기

지도와 함께 시간축을 제공한다.

```text
민원 접수 → 현장 조사 → 원인 확인 → 조치 시행 → 회신 → 종결/재발
```

같은 핀에서 시간이 지날수록 기록이 추가되므로, “민원이 많다”보다 “어떤 문제가 반복되고 어떻게 해결되었는가”를 확인할 수 있게 한다.

## 13. 조사 품질과 신뢰도

조사 결과에는 결론만 저장하지 않고 다음 요소를 함께 기록한다.

- 주장: 제보자가 말한 내용
- 확인 사실: 문서·현장·측정으로 확인된 내용
- 추정: 아직 확정할 수 없지만 가능성이 있는 원인
- 반대 근거: 사실과 다를 가능성을 보여주는 자료
- 판단: 담당자가 내린 조사 결론
- 신뢰도: 높음·중간·낮음 또는 수치 점수

AI가 요약·분류를 보조할 수는 있지만, 원인 확정·공개 핀 등록·민원 종결은 담당자 검토를 거친다. 원문에 없는 위치나 원인을 자동으로 만들어내지 않는다.

## 14. 도입 후 데이터가 만들어내는 기능

민원 핀이 누적되면 다음 기능으로 확장할 수 있다.

### 14.1 사업 사전 점검

새 사업 주소를 입력하면 주변 과거 사례와 도입 후 조사 사례를 함께 보여준다.

- 같은 시설·사업자·지역의 반복 민원
- 주변에서 자주 발생한 쟁점
- 과거 조치의 효과와 재발 여부
- 주민 협의 전에 준비할 설명·검토 항목

### 14.2 반복 원인 분석

- 특정 지역·시간대·설비 유형에 반복되는 민원
- 접수는 많지만 확인되지 않는 유형
- 같은 원인으로 여러 지점에 영향을 준 사건
- 조치 후에도 재발하는 문제

### 14.3 대응 우선순위

긴급도, 영향 범위, 반복성, 확인된 위험, 미조치 기간을 바탕으로 담당자가 먼저 조사할 민원을 정렬한다.

### 14.4 정책·설계 개선

누적 데이터를 통해 이격거리, 배수, 경관, 주민 협의, 공사 관리 등 어떤 사전 검토가 실제 민원 감소에 도움이 되었는지 확인한다.

## 15. MVP 운영 범위

초기 운영에서는 다음 범위로 시작한다.

1. 설치 예정지 주소 입력과 AI 사전점검 리포트
2. 민원 접수 폼과 접수번호 발급
3. 담당자용 민원 목록·상태 변경
4. AI의 민원 유형·위치·원인 후보 추출
5. 주소·지도 기반 위치 등록
6. 조사 결과와 증빙 업로드
7. `confirmed`·`partially_confirmed` 사건의 핀 등록
8. AI의 유사 사례·중복·후속 사건 연결 제안
9. 기존 핀과 중복·후속 민원 연결
10. 핀 상세의 시간순 이력
11. 과거 공개 `conflict_case`와 유사 사례 조회
12. 사실·추정·권고를 구분한 근거 기반 설명
13. 개인정보 마스킹과 공개 수준 설정
14. AI 결과·변경 이력·검토자·근거 보존

초기에는 AI의 원인 확정, 자동 핀 공개, 민원인의 공개 투표, 사업 허가 가능성 예측을 범위에 넣지 않는다. AI는 분석 초안과 근거 연결을 담당하고, 원인 확정·공개 핀 등록·민원 종결은 담당자가 승인한다.

## 16. 성공 지표

| 지표 | 의미 |
|---|---|
| 조사 전환율 | 접수 민원 중 조사에 착수한 비율 |
| 위치 확인률 | 원인 위치 또는 영향 위치를 확인한 비율 |
| 근거 연결률 | 조사 결론에 증빙이 연결된 비율 |
| 중복 처리율 | 기존 사건으로 정확히 연결한 비율 |
| 핀 품질 | 공개 핀 중 위치·상태·쟁점이 검토된 비율 |
| 평균 처리 기간 | 접수부터 1차 회신·종결까지 걸린 시간 |
| 재발률 | 조치 후 같은 원인으로 다시 접수된 비율 |
| 사전 활용률 | 새 사업 검토에서 과거 핀을 참고한 비율 |

핵심 성과는 핀의 개수가 아니다. **접수된 민원이 근거 있는 조사 기록으로 전환되고, 그 결과가 다음 대응에 실제로 활용되는가**가 핵심이다.

## 17. 운영 원칙

1. 접수 위치와 원인 위치를 구분한다.
2. 민원 주장과 확인 사실을 구분한다.
3. 좌표가 없으면 임의의 정확한 위치를 만들지 않는다.
4. 기존 사건과 중복 여부를 먼저 확인한다.
5. 검증 전 내용은 내부 검토 상태로 둔다.
6. 모든 결론에 조사자·시점·근거를 연결한다.
7. 개인정보와 명예훼손 가능성이 있는 정보는 공개하지 않는다.
8. 상태 변경과 핀 수정 이력을 삭제하지 않고 보존한다.
9. 지도 핀은 민원 건수가 아니라 조사된 사건을 표현한다.
10. 루체라는 판단을 대신하는 시스템이 아니라, 더 빠르고 정확한 판단을 돕는 시스템으로 운영한다.

## 18. 한 문장 요약

**루체라는 설치 예정지 주소를 입력하면 과거·현재 민원 데이터를 바탕으로 왜 설치를 재검토해야 하는지 근거와 함께 설명하고, 도입 후 접수되는 민원을 조사해 원인·위치·조치 결과를 다시 지도에 기록함으로써 시간이 지날수록 지역의 문제와 해결 경험이 축적되는 플랫폼이다.**
