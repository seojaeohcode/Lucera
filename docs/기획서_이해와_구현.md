# 기획서 이해와 구현 정리

## 1. 기획서의 실제 제품 정의

루체라는 태양광 사업의 허가 여부를 자동 결정하는 시스템이 아닙니다. 사업지 주소를 입력하면 그 주소 주변 또는 같은 행정구역에서 과거에 어떤 주민 반대·민원·협의·환경 쟁점이 있었는지 찾아서, 담당자가 설명·검토·협의를 더 일찍 시작하게 돕는 근거 조회 도구입니다.

기획서의 핵심 문장은 다음 네 가지로 정리됩니다.

| 기획서 요소 | 구현 의미 |
|---|---|
| 주소 입력 | 입력값을 원문 주소, 정규화 주소, 행정구역, 좌표 후보로 분리 |
| 주변 기록 지도 | 정확 좌표가 있을 때만 거리 계산, 없으면 읍·면·리·시·군 연결 |
| 쟁점 요약 | 문서 전체가 아니라 발언/문단별로 쟁점과 찬반 방향 저장 |
| 근거 원문 | 문서·페이지·문단 ID와 출처 URL을 모든 결과에 연결 |

## 2. 이번 구현 범위

### 구현 완료

- SQLite + FTS5 기반 실행 가능한 로컬 DB
- 운영 전환용 PostgreSQL/PostGIS 스키마
- 국회도서관 지방의정포털 회의록 목록/상세 API 수집기
- HTML 회의록을 페이지 1개와 발언/문단 단위로 분해
- 쟁점 사전과 규칙 기반 1차 분류
- 팀 제공 키워드의 고정밀 수집 전략: 태양광 앵커 + 문제어 조합, 빛반사 계열 단독 예외
- 개인정보(전화번호·이메일·주민등록번호) 검색용 텍스트 마스킹
- 도로명주소 API를 통한 전체 주소 보정 및 주소 조회 이력 저장
- 행정구역 fallback, 반경 검색, 유사 사례 그룹화
- 원문 근거·출처·장소 정밀도·거리 상태를 반환하는 API와 화면
- 중복 적재 방지와 적재 작업 이력
- 사업 입력정보의 revision·첨부·사실 provenance 저장
- 사업 절차 6단계 snapshot/event와 과거 민원 case 연결
- 광주광역시·5개 자치구·전라남도·22개 시군 지역 카탈로그와 지역별 수집기
- 주소 행정구역 검색, 좌표가 있는 경우의 반경 검색, 좌표가 없는 사건의 위치 후보 추론

### 아직 자동화하지 않은 것

- 전국 지방의회 전체를 무제한 수집하는 스케줄러
- 모든 HWP 자동 변환
- 필지 경계 기반의 자동 확정
- 임베딩 모델을 고정한 벡터 검색
- 사람 검수 없는 AI 확정 분류
- 한전 최종 접속 승인/거절 예측

이는 누락이 아니라 기획서의 안전 원칙에 따른 경계입니다. 특히 좌표가 없는 자료를 반경 1km/3km/5km로 계산하지 않고, `same_admin_area` 또는 `same_village`로만 보여주는 것이 핵심입니다.

## 2A. 광주·전남 지역 범위와 수집 정책

검색·수집 대상은 다음 27개 단위로 고정한다. 광주광역시와 전라남도는 상위권역 메타데이터이며 목표 건수 대상이 아니다.

| 범위 | 대상 |
|---|---|
| 광주 | 동구, 서구, 남구, 북구, 광산구(5개 자치구) |
| 전남 | 전라남도, 목포·여수·순천·나주·광양 5개 시, 담양·곡성·구례·고흥·보성·화순·장흥·강진·해남·영암·무안·함평·영광·장성·완도·진도·신안 17개 군 |

각 지역은 `lucera/regions.py`와 DB의 `administrative_region`에 `region_code`, 표시명, 도, `region_group`(자치시·자치군·자치구), 유형, 상위권역, CLiK `assembly_id`, 별칭으로 관리합니다. API에서 의회 ID가 확인되지 않은 지역도 목록에는 포함하되 `available=false`로 표시합니다. 이는 주소 검색 카탈로그와 문서 수집 가능 목록을 분리하기 위한 것입니다. 현재 광산구는 이 상태로 보고하며, 다른 지역 회의록을 광산구 자료로 대체하지 않습니다.

지역 수집은 `lucera/regional_collect.py`가 다음 순서로 수행합니다.

```text
지역 카탈로그
  → 고정밀 쿼리별 목록 후보
  → 지역 assembly_id와 DOCID 검증
  → 기존 DOCID 제외
  → 상세 API 원문 수신
  → 원문/문단/문장/쟁점/장소/episode/case 파이프라인
  → 지역별 processed_count·shortfall·실패사유 보고
```

목록의 총건수는 “민원 사건 수”가 아니며, 상세 원문 적재 성공 건수도 “서로 다른 민원 수”와 같지 않다. 한 문서에 여러 episode가 있을 수 있고, 여러 문서가 하나의 case를 반복할 수 있기 때문이다. 지역당 10건은 현재 MVP의 상세 문서 수집 목표로 취급하며, 고정밀 색인 결과가 부족하면 `shortfall`로 남긴다. 이전 실행에서 목표를 초과한 원문은 삭제하지 않고 보존한다. 수집기는 DOCID 기반으로 재개 가능하고, 일일 API 한도에 도달하면 `paused_quota`로 중단한다.

## 3. 데이터 흐름

```text
국회도서관 API
  → source_document 원문/해시/출처
  → document_page 문서 본문
  → meeting_segment 발언·문단
  → place_mention 장소 표현
  → canonical_place 표준 장소/정밀도
  → segment_place_link 장소-근거 연결
  → segment_issue 쟁점/찬반/근거 문장
  → sentences 문장 단위 원문 오프셋
  → keyword_mentions 키워드 발생 위치
  → episodes 회의 안에서 이어진 사건
  → conflict_case 여러 회의에 걸친 동일 민원 후보
  → case_evidence 사건-문단-문장 근거
  → 주소 입력 + 공간/행정구역/키워드 검색
  → evidence_id가 붙은 근거 결과
```

위치 추론은 회의 개최지와 민원 사업지를 분리한다. 회의록의 도·시군·읍면·리·도로명·지번·건물 표현은 원문 장소(`place_mention`)와 표준 장소(`canonical_place`)로 보존하고, 사건에 연결되는 후보는 `case_location_candidate`에 별도로 기록한다. 필지·건물·도로명 좌표가 명시되거나 주소 API에서 확인되면 높은 정밀도로 순위화한다. 읍면·리만 확인되면 그 행정구역과 근거 문단은 저장하지만 중심점 좌표를 설치지로 만들어내지 않는다.

## 3C. 사업 입력 사용자 흐름과 DB 흐름

사업 입력의 `project_id`는 사용자가 조회하려는 현재/예정 사업의 식별자이고, 회의록에서 추출된 과거 민원의 `case_id`와 다릅니다. 한 사업을 수정 제출하면 기존 행을 덮어쓰지 않고 `project_intake_submission`과 `project_application`에 revision을 추가합니다.

```text
사업 입력 제출
  → project_intake (사업 루트, project_id)
  → project_intake_submission (원본 payload + 검증 결과 + revision)
  → project_application (신청자·사업 기본정보)
  → project_site / equipment / finance / schedule / grid
  → project_permit_checklist / project_resident_risk
  → project_attachment (첨부 파일 상태)
  → project_fact (각 필드의 값·단위·출처·페이지·근거문장·신뢰도)
  → project_location_link (사이트·건축물·계통연계 후보 장소)
  → project_stage (6단계 현재 상태)
  → project_stage_event (날짜·민원·검토의 단계별 이력)
  → project_case_link (과거 conflict_case 비교 후보, pending 검수)
```

6단계는 다음과 같이 고정합니다.

| 순서 | stage_code | 연결 입력/판정 |
|---:|---|---|
| 1 | `application` | 발전사업 신청일 |
| 2 | `power_generation_permit` | 발전사업허가일 |
| 3 | `development_environment_review` | 개발행위·도시관리계획·환경 검토 필요 여부 |
| 4 | `resident_consultation_complaint` | 주민동의·공사동의·민원·민원 유형 |
| 5 | `construction_completion` | 공사 시작일·준공 예정일·사업개시일 |
| 6 | `grid_connection_operation` | 계통연계 지점·전압·변압기·사업개시일 |

좌표는 필수로 만들지 않습니다. 주소가 읍면리 수준이면 `canonical_place`에 그 수준의 `geo_precision`과 행정구역만 저장하고, 좌표가 실제로 제공되거나 주소 API에서 확인된 경우에만 위도·경도를 저장합니다. 따라서 같은 장소인지 판단할 때도 주소/필지/리/읍면/시군 단서를 각각 보존하며, 시군만 같다는 이유로 과거 민원을 자동 연결하지 않습니다.

첨부파일은 업로드 메타데이터와 추출 상태를 먼저 저장하고, 추출된 값은 `project_fact.source_attachment_id`, `source_page`, `source_excerpt`, `confidence`로 원본까지 되짚을 수 있게 합니다. 사용자 입력값도 `source_kind=user_input`인 fact로 저장하므로 화면의 현재값과 “어디서 나온 값인지”를 같은 방식으로 조회할 수 있습니다.

## 3A. 키워드 판별 원칙

팀이 제공한 키워드는 여섯 목록을 그대로 OR 검색하지 않는다. `사업·설비`는 태양광 주제 앵커로 사용하고, 실제 민원 후보는 다음 네 가지 상위 문제 카테고리로 정리한다.

| 상위 카테고리 | 대표 세부 쟁점 |
|---|---|
| 주민·민원·갈등 | 민원, 반대, 갈등, 분쟁, 주민설명회, 주민동의 |
| 입지·토지·인허가 | 이격거리, 개발행위허가, 염해농지, 농지, 산지, 용도지역 |
| 피해·환경·안전 | 빛반사, 반사광, 경관, 소음, 환경영향, 생태, 재해, 안전 |
| 수익·보상·지역경제 | 보상, 수익, 소득, 발전기금, 임대료, 지역경제, 일자리 |

`빛반사`, `반사광`, `눈부심`은 태양광 단어가 같은 문단에 없어도 고정밀 후보로 허용한다. `이격거리`, `염해농지`, `허가`, `주민`, `환경`, `안전`, `협의` 등은 태양광 앵커 또는 태양광 회의 안건과 함께 있고, 추가 문제어가 확인될 때만 쟁점으로 생성한다. `조례`, `법령`, `행정사무감사` 등은 민원 판정어가 아니라 행정 대응을 설명하는 보조어로 저장한다.

`source_document.raw_payload_json`과 `document_page.text_original`은 재처리·감사를 위한 보존 계층입니다. 화면/검색에 사용하는 `text_redacted`와 AI 입력은 별도 값입니다.

## 3B. 민원 사건 묶기 로직

키워드 발생을 곧바로 민원 사건으로 저장하지 않습니다. 하나의 근거가 다음 계층을 거칩니다.

```text
문서 → 문단/발언블록 → 문장 → 키워드 발생지점 → episode → case
```

- `meeting_segment`는 회의록의 원문 문단·발언블록입니다.
- `sentences`는 문단 안의 문장과 원문 기준 `char_start/char_end`를 저장합니다.
- `keyword_mentions`는 팀 키워드 전체의 발생 위치를 저장하지만, 일반어 발생만으로 사건을 만들지 않습니다.
- `episodes`는 한 회의 안에서 연속적으로 논의된 사건입니다. 키워드가 있는 문장과 앞뒤 1개 문단은 `episode_evidence`로 연결합니다.
- `conflict_case`는 여러 회의에서 반복되는 실제 민원 후보입니다. 사업명·주소·리·읍면·시설유형 같은 강한 식별자가 있을 때만 자동 연결하고, 그 외에는 episode별 임시 case로 남깁니다.
- `case_link_candidate`는 같은 시·군 안에서 일부 단서가 겹치지만 동일 민원으로 확정하기 부족한 쌍을 별도 검수 대상으로 남깁니다.

episode 병합 점수는 같은 문서 `0.25`, 같은 안건 `0.20`, 쟁점 겹침 `0.15`, 장소·사업·시설 식별자 겹침 `0.30`, 문단 근접성 `0.05~0.10`을 합산합니다. `또 다른 민원`, `다음 안건`, `다른 사업`, `별도로` 같은 전환어 또는 문단 간격 5 초과는 강제 분리합니다. 따라서 바로 옆 문단에서 `태양광 허가 → 주민 반대 → 빛반사 피해`처럼 쟁점이 바뀌어도 동일 안건·근접성이 유지되면 하나의 episode로 묶이고, 명시적인 새 민원 전환은 별도 episode가 됩니다.

자동 생성된 episode와 case는 `review_status=pending`입니다. 검색 API는 문단 결과에 `case`, `episode`, `evidence_role`을 함께 반환하고, 같은 case에 속한 결과는 `case_groups`로도 확인할 수 있습니다.

## 3D. 주소·거리 검색의 판정 순서

```text
입력 주소/좌표
  ├─ 도·시군구·읍면동·리 정규화
  ├─ 도로명/번지 숫자가 있으면 주소 API 후보 확인
  ├─ case_location_candidate와 행정구역 비교
  └─ 입력 좌표 + 근거 좌표가 모두 있을 때만 거리 계산
```

거리값은 “민원이 난 태양광 설치지”를 자동으로 확정한 값이 아니다. 사건의 후보 장소 중 `parcel/building/road_address/jibun_address`와 좌표가 있는 후보를 우선하고, 장소-문단 관계(`subject_site`, `nearby`, `same_village` 등)와 원문 근거를 함께 고려한다. 좌표가 없는 `ri/eup_myeon/city_county` 후보는 같은 리·읍면·시군 결과로만 반환하며 거리값은 `null`이다. `representative_place_id`는 검색 편의를 위한 대표 후보이고, 최종 설치 필지 확정은 사람 검수 또는 공식 주소·좌표 근거가 필요하다.

## 4. API 키 사용

사용자가 제공한 `API Keys.docx`의 두 공공데이터 인증값을 로컬 `config.py`에 정리했습니다.

- 도로명주소 API 키: 주소 입력이 숫자를 포함한 도로명/번지 형식일 때 사용
- 국회도서관 지방의정포털 키: `ingest-clik`에서 회의록 목록/상세 API 호출에 사용

환경변수가 있으면 환경변수가 우선합니다. `config.py`는 `.gitignore`에 포함되어 있으므로 공개 저장소에 키가 올라가지 않도록 했습니다.

국회도서관 회의록 API는 목록/상세 REST API를 제공하며, 호출당 100건 이하와 일일 키당 호출 제한이 있으므로 수집 CLI에서 요청 건수를 제한합니다.

## 5. 검색 결과 해석

검색 결과의 위치 그룹은 확정도 순서가 아니라 “어떤 연결로 찾았는가”를 표현합니다.

| 그룹 | 의미 | 거리 표시 |
|---|---|---|
| `exact_site` | 필지/건물/도로명 좌표가 있고 150m 이내 | `exact` |
| `nearby` | 좌표가 있는 다른 장소가 반경 안 | `exact` |
| `same_village` / `same_ri` | 같은 리 단위 표현 | `unknown` |
| `same_admin_area` | 같은 읍·면·동 또는 시·군·구/회의기관 지역 | `unknown` |
| `comparative_case` | 입력 지역과 공간 연결은 없지만 쟁점/키워드가 유사 | `unknown` |

`same_admin_area`의 “같은 지역”은 사업지 확정이 아닙니다. 회의 개최 기관의 행정구역만 확인된 경우에도 해당 그룹이 될 수 있으며, 결과의 `basis`에 그 사실을 적습니다.
