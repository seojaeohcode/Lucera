# Lucera · SolarCheck

영암군 태양광 사업의 주소 하나를 시작점으로, 주소·허가 원장·회의록·조례·지도 영상을 한 번에 연결하는 근거 기반 사전점검 서비스입니다.

Lucera는 허가 또는 불허를 자동 결정하지 않습니다. 담당자가 “이 위치에서 어떤 기준을 먼저 확인해야 하는가”, “과거에 어떤 갈등과 협의가 있었는가”, “다음에 어떤 자료를 준비해야 하는가”를 빠르게 파악하도록 돕습니다.

## 1. 해결하려는 문제

태양광 설치 검토는 한 가지 데이터만 조회해서 끝나지 않습니다.

1. 입력한 주소가 실제 영암군 어느 읍·면·리에 해당하는지 확인해야 합니다.
2. 조례의 주거지·도로 이격거리와 시행일을 확인해야 합니다.
3. 과거 회의록에서 같은 지역의 주민 반대, 환경 훼손, 절차, 보상, 계통 문제를 찾아야 합니다.
4. 허가 원장에 등록된 주변 사업의 규모·상태·분포를 확인해야 합니다.
5. 항공영상과 공간정보를 보며 주변 배치와 입지 특징을 함께 살펴야 합니다.

기존 방식은 각각의 자료를 따로 검색하고, 검색 결과가 실제 사업지와 어떤 관계인지 사람이 다시 판단해야 했습니다. Lucera는 이 과정을 주소를 기준으로 묶고, 검색된 문단과 규칙 계산 결과를 하나의 `evidence pack`으로 만들어 설명합니다.

## 2. 핵심 가치

| 가치 | 구현 방식 |
|---|---|
| 주소 중심 | 도로명주소·지번주소를 정규화하고 영암군 읍·면·리와 좌표를 연결 |
| 근거 중심 | 회의록 전체가 아니라 실제로 선택된 발언·문단·문장과 출처 URL을 반환 |
| 위치 정밀도 보존 | 필지 좌표와 읍·면 단위 기록을 구분하고, 좌표가 없으면 임의 중심점을 만들지 않음 |
| 숫자 안전성 | 거리·면적·용량·건수는 규칙 엔진과 DB에서 계산하고 Claude가 새로 계산하지 못하게 제한 |
| 대화 연속성 | 최초 분석 결과를 같은 `conversation_id`에 저장하고 후속 질문에 문맥으로 전달 |
| 멀티모달 | VWorld 항공영상과 사용자가 첨부한 이미지를 Claude의 이미지 입력으로 전달 |
| 담당자 친화성 | 긴 답변 대신 판단 카드·근거·다음 확인 항목·답안 인포그래픽으로 제공 |

## 3. 전체 사용자 플로우

화면은 세 단계로 구성됩니다. 앞 단계가 완료되어야 다음 단계가 열리며, 각 단계의 처리 중에는 AI 분석·주소 변환·대화 준비 상태를 로딩 애니메이션으로 보여줍니다.

### 3.1 1단계: 민원 사례 선택

주소를 직접 입력해 복잡한 양식을 채우는 대신, 영암군에서 발생할 수 있는 민원 유형 5개 중 하나를 선택합니다.

| 유형 | 화면에서 다루는 질문 | 사례에 자동 입력되는 내용 |
|---|---|---|
| 규제·인허가 | 조례·허가·주거지·도로 이격거리 기준을 충족하는가 | 주소, 민원 제목, 이격거리·허가 확인 요청 |
| 입지·환경 훼손 | 농지·배수·토사·경관·조망에 영향이 있는가 | 주소, 환경 상황, 보완 확인 요청 |
| 절차·주민수용성 | 주민 고지·설명회·협의가 있었는가 | 주소, 주민 의견수렴 상황, 회의록 확인 요청 |
| 이익배분·사업 신뢰 | 주민참여·마을기금·보상·사업자 약속이 확인되는가 | 주소, 수익 배분과 약속 이행 확인 요청 |
| 계통·송전 | 계통 접속·송전선로·변전 설비를 어떻게 확인하는가 | 주소, 접속 가능성과 지연 사례 확인 요청 |

사례를 누르면 주소와 실제형 민원 문장이 함께 채워집니다. 사용자는 예시를 그대로 제출하거나 문장을 수정할 수 있습니다. UI의 사례 목록은 `GET /v1/cases`에서 받으며, 서버 연결이 없을 때도 화면 확인이 가능하도록 동일한 구조의 fallback 사례를 둡니다.

### 3.2 2단계: AI 분석·핀 저장

“민원 분석하고 좌표 저장”을 누르면 다음 순서로 처리됩니다.

1. 입력 주소와 민원 문장을 정규화합니다.
2. 도로명주소 또는 지번주소의 숫자를 확인하고 주소를 지오코딩합니다.
3. 영암군 주소인지 검증합니다. 영암군 밖의 주소는 분석하지 않습니다.
4. VWorld에서 분석 위치 주변의 항공영상·배경지도·공간정보를 조회합니다.
5. 민원 유형과 문장에서 쟁점 코드를 분류합니다.
6. 회의록 문단, 장소 연결, 과거 사건, 허가 원장, F1/F3/F4 정보를 검색합니다.
7. 조례와 입력값을 규칙 엔진으로 비교합니다.
8. 검색·계산 결과를 `evidence pack`으로 묶고 Claude 또는 로컬 답변기로 문장을 만듭니다.
9. 민원·좌표·분석 결과·근거 연결·대화 시작 메시지를 DB에 저장합니다.
10. 분석 결과와 함께 영암군 지도에 사용자 민원 핀을 표시합니다.

분석 화면은 긴 원문을 먼저 보여주지 않고 다음 순서로 요약합니다.

- 현재 판단: 설치 재검토 필요·조건부 검토·주의해서 검토·판단 보류 등
- 분석 위치: 확정된 주소와 위도·경도
- 한눈에 보는 판단: 핵심 신호 카드 최대 5개
- 연결된 근거: 실제 회의록 문단 발췌와 출처
- 지금 확인할 것: 담당자가 다음에 확인할 체크리스트
- AI 설명 원문: 필요할 때만 펼쳐보는 상세 답변

주거지·도로 이격거리 카드에는 클릭 가능한 시각화 목업이 있습니다. 설치 예정지 좌표를 중심으로 기준 반경을 그리고, 입력된 거리와 겹치는 모습을 지도에 표시합니다. 기준 반경은 옅은 빨간색, 입력 거리 비교선은 점선으로 표현하며, 이는 이해를 위한 시각화이고 실제 허가 판정값은 규칙 엔진의 수치만 사용합니다.

### 3.3 3단계: 주소·챗봇

2단계에서 저장한 주소를 확인하면 같은 `conversation_id`를 사용하는 챗봇이 열립니다.

- 최초 분석 답변을 대화 첫 메시지로 표시합니다.
- 사용자의 후속 질문은 기존 주소·분석·최근 대화 문맥과 함께 다시 검색합니다.
- 질문마다 회의록 근거와 지도 영상을 다시 연결합니다.
- 질문 결과 아래에 답변 내용을 한 장의 인포그래픽 슬라이드로 생성합니다.
- 슬라이드를 누르면 팝업에서 크게 볼 수 있습니다.
- 분석에 사용한 VWorld 항공·배경 영상도 마지막에 함께 표시합니다.
- 이미지 썸네일을 누르면 지도 영상을 팝업으로 확대합니다.
- PNG, JPEG, WEBP, GIF 현장 이미지를 추가할 수 있습니다.

챗봇은 “기능을 켰을 때만 일부 데이터가 들어가는 방식”이 아닙니다. 주소, 민원 유형, 과거 대화, 회의록 근거, 조례 규칙, 허가 원장, F1/F3/F4 문맥, VWorld 영상이 가능한 범위에서 매 요청마다 자동으로 하나의 분석 묶음에 들어갑니다.

## 5. RAG 처리 방식

Lucera의 RAG는 “LLM에게 모든 원문을 던지고 알아서 답하게 하는 방식”이 아닙니다. 먼저 코드가 주소·규칙·검색·근거를 계산하고, Claude는 검증된 결과를 짧은 한국어 답변으로 표현합니다.

### 5.1 입력 정규화

`RAGService.analyze()`가 모든 분석의 시작점입니다.

- 민원 문장 공백과 길이를 정리합니다.
- 주소에서 시·군·읍·면·리·도로명·지번을 추출합니다.
- 부지면적·설치면적·용량·최단 주거지 거리·최단 도로 거리의 숫자와 단위를 읽습니다.
- 사용자가 위도·경도를 주면 입력 좌표로 사용합니다.
- 좌표가 없고 주소에 도로번호·지번이 있으면 주소 API와 VWorld 지오코딩을 시도합니다.
- 읍·면·리만 있는 주소에는 임의의 건물이나 행정구역 중심점을 설치지 좌표로 만들지 않습니다.

### 5.2 쟁점 분류

화면의 5개 민원 유형과 내부 검색 쟁점 코드를 분리합니다.

| 화면 유형 | 내부 대표 쟁점 코드 |
|---|---|
| 규제·인허가 | `siting_permit_regulatory` |
| 입지·환경 훼손 | `safety_environment`, `landscape_damage`, `agricultural_land_damage` |
| 절차·주민수용성 | `communication_procedure` |
| 이익배분·사업 신뢰 | `external_benefit_distribution`, `communication_procedure` |
| 계통·송전 | `grid_connection` |

그 외 내부 쟁점으로 `glare_reflection`, `noise_living_discomfort`가 있습니다. `주민`, `환경`, `안전`, `협의` 같은 일반어만으로 민원을 만들지 않고, 태양광 앵커·문제어·회의 안건 문맥이 함께 확인될 때만 쟁점을 생성합니다. `빛반사`, `반사광`, `눈부심`은 태양광 단어가 같은 문단에 없어도 고정밀 후보로 허용합니다.

### 5.3 회의록 구조화

회의록은 다음 계층으로 내려가며 처리됩니다.

```text
source_document
  → document_page
  → meeting_segment       문단·발언 블록
  → sentences             문장·원문 오프셋
  → keyword_mentions      키워드 발생 위치
  → segment_issue         쟁점·방향·근거 문장
  → episodes              한 회의 안의 연속 사건
  → conflict_case         여러 회의에 걸친 동일 민원 후보
  → case_evidence         최종 검색 근거
```

장소도 별도로 구조화합니다.

```text
place_mention
  → canonical_place
  → segment_place_link
  → case_location_candidate
```

이를 통해 회의 개최지, 민원인의 거주지, 사업 부지, 피해 장소가 뒤섞이지 않도록 합니다. 시·군 이름만 같다는 이유로 사건을 같은 민원으로 병합하지 않고, 사업명·발전소명·주소·리·읍면·시설 유형 같은 강한 식별자가 있을 때만 연결합니다.

### 5.4 검색과 랭킹

현재 MVP는 SQLite FTS5 전문검색과 행정구역·좌표 검색을 결합한 하이브리드 검색입니다. 임베딩 모델이나 벡터 차원을 임의로 고정하지 않았습니다.

검색 순서는 다음과 같습니다.

1. 입력 주소와 대화의 최근 사용자 질문에서 검색어·쟁점 코드를 만듭니다.
2. FTS5에서 태양광 문맥과 문제어가 맞는 문단을 찾습니다.
3. 영암군 범위를 적용합니다.
4. 정확 좌표가 있으면 하버사인 거리로 반경을 계산합니다.
5. 좌표가 없으면 `same_ri`, `same_village`, `same_admin_area`로만 연결합니다.
6. 같은 사건의 결과를 그룹화하고, 같은 회의의 중복 문단을 줄입니다.
7. 문단의 실제 선택 지점을 중심으로 짧은 문맥 발췌를 만듭니다.

현재 검색 점수는 다음 요소를 사용합니다.

- 키워드 적합도: 0.38
- 공간 연결도: 0.32
- 회의일 최신성: 0.20
- 출처 URL 존재 여부: 0.10

공간 연결 그룹은 다음처럼 해석합니다.

| 그룹 | 의미 |
|---|---|
| `exact_site` | 필지·건물·도로명 좌표가 있고 입력 위치와 직접 연결 |
| `nearby` | 좌표가 있는 다른 장소가 검색 반경 안에 있음 |
| `same_ri` / `same_village` | 같은 리·마을 표현이 확인됨. 정확한 거리값은 확정하지 않음 |
| `same_admin_area` | 같은 읍·면·동 또는 시·군·구 수준의 연결 |
| `comparative_case` | 장소 연결은 없고 쟁점·키워드가 유사한 비교 참고 |

### 5.5 맥락에 맞는 근거 연결

근거는 문서 제목만 반복해서 보여주지 않습니다.

- 선택된 민원 유형에 맞는 쟁점 문단을 우선합니다.
- 문단의 실제 발췌 구간을 선택합니다.
- 같은 회의의 OCR 변형·중복 문단을 하나로 줄입니다.
- 한 회의에서 가장 관련성 높은 문단 하나를 우선합니다.
- 근거가 없는 경우 “현재 연결된 근거가 없다”고 표시하고, 무관한 회의록을 억지로 근거로 쓰지 않습니다.
- 각 결과에는 `evidence_id`, 회의·문서 ID, 날짜, 장소 연결 방식, 출처 URL이 포함됩니다.

### 5.6 evidence pack

검색이 끝나면 Claude에 전달할 입력을 그대로 원문 전체로 만들지 않고 필요한 정보만 압축합니다.

```text
입력 주소·민원·면적·용량
대화 최근 문맥 최대 6개 메시지
정규화된 위치
규칙 엔진 판정
쟁점별 근거와 발췌
처리 과정 timeline
허가 원장 요약과 대표 표본
F1/F3/F4 위치 문맥
VWorld 지도 영상 요약
답변의 한계
```

전달량도 제한합니다.

- 핵심 이유 최대 5개
- 이유당 근거 발췌 1개
- 발췌 최대 220자
- 처리 과정 최대 6개
- 허가 표본 최대 3개
- 지도 관찰 최대 2개
- 다음 확인 최대 4개
- VWorld 영상 최대 3장

### 5.7 답변 안전장치

Claude는 숫자나 허가 결론을 계산하는 역할이 아닙니다.

1. 규칙 엔진이 이격거리·면적·용량·건수·날짜를 먼저 계산합니다.
2. Claude는 `evidence pack` 안의 값만 사용해 JSON 형식의 답변 구조를 만듭니다.
3. 모든 이유는 허용된 `evidence_id`를 인용해야 합니다.
4. pack에 없는 숫자가 문장에 들어가면 numeric guard가 답변을 거부합니다.
5. 이미지 관찰에 거리·면적·개수 등의 숫자가 들어가면 답변을 거부합니다.
6. JSON 파싱 실패·API 오류·시간 초과·검증 실패 시 결정론적 로컬 답변기로 자동 전환합니다.

이 방식으로 Claude가 그럴듯하지만 출처 없는 숫자나 무관한 회의록을 만들어내는 문제를 줄입니다.

## 6. 멀티모달 처리

### 6.1 VWorld 지도 영상

VWorld 키가 있으면 주소의 정확한 좌표를 기준으로 다음 세 장을 조회합니다.

1. 근접 항공영상: `PHOTO`, zoom 17
2. 광역 항공영상: `PHOTO`, zoom 15
3. 광역 배경지도: `GRAPHIC`, zoom 15

추가로 다음 공간정보를 조회합니다.

- 부지 용도지역
- 반경 300m 용도지역
- 가능한 경우 지적 필지 정보

영상은 Claude가 이미지 입력으로 받아 주변 주택 밀집, 도로 배치, 농지·산지·수계, 시설 배치 같은 정성적 특징을 관찰합니다. 거리·면적·허가 여부는 영상에서 새로 측정하지 않고, 조례·허가 원장·좌표 계산 결과를 사용합니다.

지도 영상은 서버의 캐시 디렉터리에 저장하고, 브라우저에는 `/v1/map-image/{cache_key}` 형태의 제한된 URL로 전달합니다. 경로 검증을 통과한 16진수 캐시 키만 파일로 읽습니다.

### 6.2 사용자 첨부 이미지

챗봇은 PNG, JPEG, WEBP, GIF를 받을 수 있습니다.

- 이미지는 형식과 base64 유효성을 검증합니다.
- Claude API가 활성화된 경우에만 이미지 원문을 Claude 이미지 블록으로 전달합니다.
- SQLite에는 이미지 원문을 저장하지 않고 첨부 여부와 메시지 메타데이터만 저장합니다.
- 이미지에서는 주변 배치와 시설 특징을 관찰하되, 사진만으로 허가·거리·면적을 확정하지 않습니다.

### 6.3 답변 인포그래픽

Claude가 만든 구조화 답변을 브라우저에서 SVG 슬라이드로 렌더링합니다.

- 900px 기준의 세로형 한 장 요약
- 결론, 핵심 근거, 다음 확인 항목을 분리
- 채팅 첫 답변과 후속 답변마다 생성
- 썸네일 클릭 시 모달 팝업으로 확대
- 지도 영상 3장도 별도 썸네일·팝업으로 제공

따라서 긴 행정 문장을 그대로 읽지 않아도 판단의 핵심을 한눈에 확인할 수 있습니다.

## 7. Solverton F 기능

### F1에 해당하는 조례 비교 화면

화면에는 `설치 기준`으로 표시됩니다.

- 영암군만 보는 조례 조회가 아니라 전남 22개 시·군을 같은 축에 표시합니다.
- 영암군과 인접 시·군의 도로 이격거리 기준을 비교합니다.
- 국가 200m 비교선을 차트에 표시합니다.
- 현행 조례와 `2026-09-18 상한 적용` 가정 토글을 제공합니다.
- 영암군 기준 조문번호·시행일·도로 적용범위·주거 기준을 함께 표시합니다.
- 값이 없는 시·군은 임의의 숫자를 채우지 않고 확인 필요로 표시합니다.

API: `GET /v1/features/f1`

### F3에 해당하는 리별 누적 허가 화면

화면에는 `리별 허가 누적`으로 표시됩니다.

- 영암군 리별 누적 허가 건수·면적·최초연도·최근연도를 비교합니다.
- 상위 6개 리를 먼저 보여주고 전체 데이터는 API에 보존합니다.
- 리를 누르면 해당 읍·면·리의 지도 표본으로 이동합니다.
- 리별 대표 표본 좌표만 지도에 표시해 1,549개 허가 핀이 겹치는 문제를 줄입니다.

API: `GET /v1/features/f3`

### F4에 해당하는 계통 접속 신호 화면

화면에는 `계통 접속 신호`로 표시됩니다.

- 변전소 이름이나 마스킹된 이름을 보여주지 않습니다.
- 읍·면별 공개 허가 건수를 읽기 쉬운 신호로 바꿉니다.
- 0~99건: `여유`
- 100~199건: `혼잡`
- 200건 이상: `포화`
- 이 신호는 실제 한전 접속 가능 용량의 확정값이 아니며, 최종 접속 여부는 한전 확인이 필요합니다.

API: `GET /v1/features/f4`

### 8.4 좌표와 정밀도 원칙

`geo_precision`은 `parcel`, `building`, `road_address`, `jibun_address`, `village`, `ri`, `eup_myeon`, `city_county` 등으로 저장합니다.

- 필지·건물·도로명 주소 좌표가 있으면 거리 계산이 가능합니다.
- 읍·면·리만 확인된 기록에는 거리값을 만들지 않습니다.
- 회의 개최지와 사업지를 같은 장소로 간주하지 않습니다.
- 대표 좌표는 검색 편의를 위한 후보일 수 있으며, 공식 설치 필지 확정과 다릅니다.

| `CLIK_API_KEY` | 국회도서관 지방의정포털 회의록 수집 |
| `LUCERA_ANSWER_MODE` | `auto` 또는 `local` 답변 모드 |

키가 없거나 외부 API가 실패해도 핵심 규칙·검색·로컬 답변은 계속 작동하도록 설계했습니다. 다만 VWorld 키가 없으면 지도 영상이 비어 있을 수 있고, Claude 키가 없으면 결정론적 로컬 템플릿이 답변을 생성합니다.

### 로컬 환경 설정 예시

```text
LUCERA_ANSWER_MODE=auto
CLAUDE_MODEL=claude-sonnet-5
ANTHROPIC_API_KEY=
ANTHROPIC_WORKSPACE_ID=
VWORLD_API_KEY=

```

`deploy/lucera.env.example`을 참고해 로컬 `.env` 또는 NCloud `/etc/lucera/lucera.env`에 넣습니다. 실제 값이 들어간 파일은 Git에 추가하지 않습니다.

## 11. 실행 방법

### 11.1 합성 데이터로 로컬 UI 확인

$py = 'C:\Python313\python.exe'

### 11.2 서버 운영 데이터 재구축

실제 운영 데이터는 GitHub에서 내려받는 것이 아니라 서버에 별도로 배치된 입력 파일로 재구축합니다.

```powershell
& $py scripts\rebuild_yeongam_real_db.py `
  --db data\db\lucera_minutes.sqlite3 `
  --replace `
  --map-sample-target 180 `
  --geocode-workers 12
```

재구축 원칙은 다음과 같습니다.

- 허가 원장 전체는 DB에 보존합니다.
- 지도에는 리별 대표 표본 180개만 표시합니다.
- 좌표는 지번 주소를 기준으로 지오코딩합니다.
- 기존 SQLite, WAL, SHM은 `data/db/backups/`에 보관한 뒤 교체합니다.
- 회의록은 문서·문단·쟁점·장소·사건 연결을 다시 생성합니다.

## 12. NCloud 배포

Terraform 구성은 `infra/ncloud/`, 운영 파일은 `deploy/`에 있습니다.

```powershell
& .\scripts\deploy_ncloud.ps1
```

배포 스크립트는 다음을 순서대로 수행합니다.

1. Terraform output에서 서버 IP와 접속 정보를 읽습니다.
2. 코드·스키마·웹 자산·서버 전용 데이터 디렉터리를 압축합니다.
3. `/opt/lucera`에 런타임을 설치합니다.
4. Python 의존성과 Nginx·systemd 구성을 확인합니다.
5. `rebuild_yeongam_real_db.py --map-sample-target 180`을 실행합니다.
6. DB 파일 소유권을 `lucera` 사용자로 맞춥니다.
7. `lucera`와 Nginx를 재시작합니다.
8. `/health`를 최대 30회 재시도해 정상 상태를 확인합니다.

배포 시 API 키는 `/etc/lucera/lucera.env`에서만 읽으며, 압축파일·GitHub·웹 응답에 키 값을 포함하지 않습니다.

## 15. 공개 저장소 안전 정책

이 저장소를 공개 제출물로 사용할 때 다음 파일과 값은 포함하지 않습니다.

- 개인정보: 전화번호·이메일·주민등록번호 등
- 실데이터 원문: 실제 회의록·허가 원장 행·주소 좌표 캐시
- API 키: Anthropic·VWorld·도로명주소·CLiK 인증값
- 비밀번호: Terraform state, 서버 root 비밀번호, 운영 환경파일
- 실행 DB: SQLite 운영 DB와 백업·WAL·SHM

공개 저장소에는 설명·스키마·코드·합성 fixture만 두고, 실제 운영 데이터와 비밀값은 배포 서버의 접근 제한된 경로에서만 주입합니다. `config.py`도 비밀값을 보관하지 않고 환경변수 이름과 기본값만 읽습니다.

## 16. 한계와 운영 시 주의점

- 이 서비스는 사전점검·근거 조회 도구이며 법적 허가·불허를 확정하지 않습니다.
- 회의록에서 장소가 읍·면·리 수준으로만 확인되면 정확한 거리값을 만들지 않습니다.
- VWorld 영상은 주변 배치와 입지 특징을 관찰하는 입력이며, 공식 측량·조례·허가 원장을 대체하지 않습니다.
- F4의 `여유·혼잡·포화`는 공개 허가 건수 기반의 검토 신호이며 실제 한전 접속 여유 용량을 의미하지 않습니다.
- 자동 생성된 사건·장소 연결은 `pending` 검수 상태를 가질 수 있습니다.
- 최종 허가 검토에는 최신 조례 원문, 공식 주소·측량, 한전 계통 확인, 현장조사가 필요합니다.
